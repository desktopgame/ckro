# 設計
本ドキュメントは、このプロジェクトが開発するTUI型テキストエディター（以下、「本ツール」）の設計を記述するものです。

# バックエンド
本ツールはターミナルに対する描画のバックエンドに `tcell` を利用しており、
これをラップする形で各種UIコントロールやテキストボックスを描画しています。
`tview` は利用していません。

# コントロール
本ツールではあらゆるUIコントロールのことを「コントロール」、
ソースコード中では「Control」と呼称しています。

画面はコントロールの組み合わせで構成されています。
レイアウトマネージャは分離されておらず、コントロール自体がレイアウトマネージャと一体化しています。

## タイル
もっとも基本的なコントロールはタイルであり、これは単にテキストボックスを表示するだけです。
ただし、テキストボックスの内容、イベントハンドラはプレゼンターによって分離されており、
これにより多様なコントロールを実現することができます。
現時点では、ツリー、リスト、スクロールバー、行番号などがタイルで実現されています。

## ボックス
ボックスは一方向にコントロールを並べるだけのコントロールです。
それでいながら、多くのケースはボックスの組み合わせで実現することができます。
全てのコントロールは最大サイズの代わりに「フレキシブル属性」を持っており、
ボックスはこの属性によって子コントロールを引き延ばしたり、あまったサイズを分配したりします。

## フレーム
フレームは単一の子コントロールを持つことができるコントロールです。
これは単に子コントロールの周囲に飾りをつけるだけのコントロールです。

## センター
センターは単一の子コントロールを持つことができるコントロールです。
センターは子コントロールの「フレキシブル属性」を上書きして固定幅で画面中央に任意のコントロールを配置します。
ダイアログは主にこれとフレームの組み合わせで実現されます。

## スタック
スタックはZ方向に子コントロールを重ねるオブジェクトです。
これはコントロールではないので、ほかのコントロールの中に入れることはできません。

## ウィンドウ
ウィンドウはスタックのラッパーです。
フォーカス制御に加え、入れ子になったダイアログを順番にポップするための機能を持ちます。

# テキストボックス
本ツールにおいてもっとも重要であり、もっとも複雑な設計の機能です。

## 構成

### TextBox
テキストボックスの本体であり、モデル、ビューを統合して管理する構造体です。

### Document
文字列の挿入、削除を管理し、文字列を構造化された形式で出力する機能を持ちます。
テキストボックスのモデルにあたります。

### Element
Document の構造を表現するための要素です。
通常、見出し、太字、コードブロック、などなど文書構造に対応したElementが存在します。
これを入れ子にして一つの文書構造を表します。

### TextView
ある Element の中身を描画するインターフェイスです。
それだけではなく、カーソルの移動、文字の挿入位置、削除時の動作までハンドルする非常に複雑なインターフェイスです。
Element と同様、TextView は子ビューを持つことがあり、必要に応じて子ビューへ移譲するのが親ビューの責任です。
テキストボックスのビューにあたります。

### TextLayout
ある編集時点におけるレイアウト情報のスナップショットです。
全ての TextView の位置とサイズを保持しており、TextView はこれを参照して適切な位置に描画します。
ほとんどの場合、Element の構造をそのままマップした階層を持ちますが、
常に一致していることが求められるわけではありません。
例えば、描画のフォールバックのために元Elementと異なる階層構造を持ってもかまいません。

## 設計の核心
リッチテキストの表示と編集を同時に扱うにあたり、もっとも重要なルールは
「カーソルが常に可視部分を指すようにすること」です。

例えば、ある文字列をアスタリスクで囲むと太字テキストになりますが、
その瞬間にアスタリスク自体は非表示になり、内側の太字部分のテキストのみが表示されます。
この直後にカーソルを動かしたとき、カーソルがアスタリスクを指す状態になるのは正常な状態ではありません。
カーソルを動かしたら、不可視のアスタリスクはまたいで移動するのが適切です。
つまり、リッチテキストの表示と編集を同時に扱うなら、カーソル位置を単に文字列の中のインデックスとしてはいけません。

この問題に対処するために、二つの座標を持っています。

### モデル座標
モデル座標は、行、指している文字の先頭バイト、指している文字のバイト長によって表されます。
この座標は決して不可視部分を指すことはありません。
また、編集不可な飾り部分を指すこともありません。

### ビュー座標
ビュー座標は、単一の符号なし整数型の値で表されます。
この値は、0から全ての TextView の MoveLength() の和までの範囲の値を持ちます。
半開区間であり、終端は含みません。

この値さえあれば、現在カーソルがどのリッチテキストの、どの部分を指しているか解決可能になっています。
これは TextView インターフェイスによって実現されます。

#### TextView
TextView のカーソル移動に関連する部分のみを抜粋すると、以下のような感じです。

```go
type TextView interface {
	MoveLength(ctx Context, textLayout *TextLayout) int
	MoveUp(ctx Context, textLayout *TextLayout, viewLocalPos int) int
	MoveDown(ctx Context, textLayout *TextLayout, viewLocalPos int) int
	MoveLeft(ctx Context, textLayout *TextLayout, viewLocalPos int) int
	MoveRight(ctx Context, textLayout *TextLayout, viewLocalPos int) int

	ConvertPos(ctx Context, textLayout *TextLayout, viewLocalPos int) (ViewLocalX int, ViewLocalY int)
	ConvertModel(ctx Context, textLayout *TextLayout, viewLocalPos int) CharacterReference
	ConvertViewLocalPos(ctx Context, textLayout *TextLayout, bytePos model.Position) int
}
```

TextView は MoveLength() によってそのビューの中でカーソル移動可能な回数を表します。
空行の場合であっても 0 ではなく 1 を返します。
つまり、上から順に TextView の長さを足し、現在のビュー座標が開始位置を上回ったらそれが現在の TextView になるし、
ビュー座標から開始位置を引けばそのビューにおけるローカルビュー座標になるというわけです。
このローカルビュー座標が重要です。

MoveUp, MoveDown, MoveLeft, MoveRight はどれもあるローカルビュー座標を移動したあとのローカルビュー座標に変換するものです。
ビューの範囲をはみ出すときには -1 を返すルールとなっています。
カーソルを動かすときは常にこの Move シリーズのメソッドを通じてビュー座標を動かします。
そのあとで、ConvertModel を使ってモデル座標を取得します。

また、カーソル自体を描画するために現在のローカルビュー座標におけるカーソルの位置を取得できる方法も必要です。
それが ConvertPos です。これはビューの左上原点からの相対座標で2Dの位置を返します。

最後に、ConvertViewLocalPos はバイト位置をローカルビュー座標に変換するものです。
バイト位置が飾りの中を指しているときは内側に寄せられる、というルールがあります。
これを使って、文字列の挿入、削除後の正しいビュー位置を解決します。

## 制約
あらゆるコンテンツを格納可能なテキストボックスは目指しておらず、
実装コストを下げるために妥協している点があります。
が、そのうちのいくつかは将来的には撤廃されるかもしれません。
* 横方向のスクロールはサポートしない
* リッチテキストがウィンドウ幅をはみ出す場合、プレーンテキストにフォールバックして折り返す。
* ルートの TextView は行単位で空間を占める（子ビューはその限りではない）
